A small release: one feature, and the project's first written roadmap, which sets the aim: **better than Redgate SQL Backup Pro, at zero cost**.

## What's new

**`--copy-to` on `backup` and `backup-all`.** Copy each finished backup, with its manifest, to other places straight after taking it:

```text
sqlsqueeze backup [app] zstd "aes(passwordEnv=KEY)" "local(path=/backups/app_{yyyyMMdd_HHmmss}.bak)" \
    --copy-to "local(path=/mnt/nas/app.bak)" --copy-to "s3(...)" --copy-to "azure(...)"
```

- Repeatable, for a second disk or share, S3 and Azure.
- The copy finds the file by the name the backup *actually* used, so date-stamped names work.
- It retries through outages for up to 24 hours (`--copy-max-hours`, `--copy-backoff-seconds`) and resumes unfinished S3 and Azure uploads, exactly like `copy`.
- **A failed copy never fails the backup.** The backup is kept, every other destination is still tried, the failure is reported (`copies` and `copyProblems` in `--json`), and the exit code is non-zero so cron notices. Retry just the copy with `sqlsqueeze copy`.
- With `backup-all`, put `{database}` and `{backuptype}` in each `--copy-to` path; several databases into one copy-to path are refused before anything is backed up.

**[ROADMAP.md](https://github.com/yantra3loka/sqlsqueeze/blob/master/ROADMAP.md).** Two rules: nothing in the product, or in building, testing and releasing it, costs anything (free GitHub tiers, free SQL Server editions, free emulators), and "better than Redgate" is only claimed once it has been measured and the measurement published. Then where SqlSqueeze stands against Redgate feature by feature, what is next and why (real SQL Server in free CI on Windows and Linux across versions, S3 and Azure conformance without paid accounts, authenticated encryption), the features meant to put it ahead (automatic proof-of-recovery drills, public-key encryption with immutable destinations, RPO monitoring, policy as code), what is not planned, and the decisions that need the owner (none of which cost money).

## Still true from v1.5.0

If you are upgrading from v1.4.0 or earlier, read the [v1.5.0 notes](https://github.com/yantra3loka/sqlsqueeze/releases/tag/v1.5.0): backups made with `zstd` followed by another stage (such as `aes`) before v1.5.0 cannot be restored, and failed backups to S3 or Azure could leave truncated objects.

## Known limits

- Tested live on SQL Server 2022 on Linux, with moto and Azurite standing in for S3 and Azure. The new commands have not been run against a Windows SQL Server, and nothing has been tried against real S3 or Azure accounts. Closing both, for free and on every change, is first on the roadmap.
- `restore-chain` reads local folders only; `test-restore` handles full backups only.
- On Linux, build the VDI shim on the SQL Server machine (`cd native/linux && make`, needs g++; the source is in the download) and run as the `mssql` user.
