## Upgrade notes: please read

**Two bugs in v1.4.0 and earlier could leave you without a restorable backup. Both are fixed here.**

- **`zstd` followed by another stage (for example `zstd aes(...)`) wrote backups that cannot be restored.** The `zstd` stage did not close the stage after it, so `aes` never wrote its final block. `zstd` alone and `gzip aes(...)` were not affected. **Take new backups of anything made with `zstd` followed by another stage, and do not rely on the old ones.** The new `verify` command catches this.
- **A failed backup to S3 or Azure Blob left a truncated object that looked like a backup.** If SQL Server aborted a backup part-way, the cloud writer still completed its upload. Such objects are not usable. Backups taken with this version always have a `<name>.manifest.json` beside them, so an object with no manifest is either from an older version or unfinished: if you know a backup failed, delete what it left behind.

Smaller fixes: differential backups no longer fail on patched SQL Server builds (`RTM-CU27`, `RTM-GDR`, ...); backups owned by another user or on read-only storage can be restored and verified; gzip, bzip2, zip64 and zstd accept `level=` on restore so one pipeline string works both ways; `prune` no longer loops forever on S3 and Azure; the cron wrapper and PowerShell module no longer mistake the SQL Server VDI library's abort notice for the result.

## What's new

**Know your backups are good**
- `verify <storage> [pipeline...]`: re-reads a backup through its pipeline and compares size and SHA-256 with a manifest written at backup time. No SQL Server needed.
- `verify --sql`: also has SQL Server read the whole backup (`RESTORE VERIFYONLY` through a virtual device), so compressed and encrypted backups can be checked by SQL Server itself.
- `test-restore`: restores a full backup into a scratch database, runs `DBCC CHECKDB`, and drops it. The only check that finds a corrupt database inside a perfectly valid backup.
- Backups now write `<file>.manifest.json` (local) or an object beside the backup (S3, Azure): database, backup type, files, pipeline (secrets are never stored), sizes and hashes.

**No lock-in, no retyping**
- `unpack`: turns a backup back into the plain native `.bak` (checked against the manifest). `RESTORE DATABASE ... FROM DISK` works on it with no SqlSqueeze involved.
- `--from-manifest` (on `unpack`, `restore`, `verify`, `test-restore`): takes the pipeline from the manifest.

**Many databases, and chains**
- `backup-all`: `USER_DATABASES`, `SYSTEM_DATABASES`, `ALL_DATABASES`, names, wildcards and `-exclusions`; `{database}` and `{backuptype}` in storage paths; a differential or log backup with no full backup to build on becomes a full one; one failing database does not stop the rest.
- `restore-chain <folder> <database>`: restores the latest full + differential + logs from the manifests in a folder, `--stopat` for a point in time, `--as` to restore under another name, `--norecovery` / `--standby`, `--dry-run`.
- `restore --kill-connections` ends other sessions first (and puts the database back to multi-user if the restore fails); orphaned users are reported as a warning after a restore.

**Copies that survive the network**
- `copy <source> <destination>`: copies a finished backup and its manifest as stored. Retries through outages with a growing wait for up to 24 hours, refuses a source that does not match its manifest, and **resumes unfinished S3 and Azure uploads**: parts the server already holds with identical content are not sent again.

## Known limits

- The new commands were exercised live against SQL Server 2022 on Linux, with moto and Azurite standing in for S3 and Azure. Windows runs the unit tests in CI, but the new commands were not run against a Windows SQL Server. **Nothing has been tried against real S3 or Azure accounts yet.**
- `restore-chain` reads local folders only and picks by the time each backup was taken (SQL Server still checks log sequence numbers, so a gap fails instead of restoring wrongly). `test-restore` handles full backups only.
- On Linux, build the VDI shim on the SQL Server machine: `cd native/linux && make` (needs g++); its source is in the download. Run SqlSqueeze as the `mssql` user.
- `backup` has no built-in `--copy-to`; copying is a second command.

Full details and live-test results are in the [README](https://github.com/yantra3loka/sqlsqueeze#readme).
