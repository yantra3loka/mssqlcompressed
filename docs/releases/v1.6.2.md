A bug-fix release for **everyone using the `s3` or `azure` storage**, found by the new cloud conformance run.

## Fixed

- **S3 requests were not signed the way AWS requires.** Two bugs, both invisible to the mocks the tests used (moto and the unit-test fakes do not check signatures): the `x-amz-content-sha256` header, which S3 insists on, was never sent, and a query string containing a slash (every prefix such as `db/app/`, used by `prune` and by resuming an upload) was encoded twice. Strict S3 servers rejected the requests with `SignatureDoesNotMatch` or "missing header". **v1.6.1 and earlier were very likely rejected by real AWS S3** and by other services that check signatures; they only ever ran against moto. The signer now reproduces, exactly, the signature AWS prints in its own documentation example, and a second test checks an independently computed signature for a query with a slash, space and plus.
- **Azure blob names with `%`, `#`, spaces or other special characters** were stored under a different name (`%41` became `A`) or cut short at `#`, or failed with a 403. They are now percent-encoded in the URL and in the signature.

## New

- **Cloud conformance.** `tools/cloud-conformance/run.sh` runs 25 storage scenarios against any S3-compatible service or Azure Blob account (multipart uploads, a part-aligned and a one-byte object, awkward names, overwrite, integrity checked in place, bit-identical download, a copy killed half way and resumed, a wrong secret, prune), with no SQL Server needed. CI runs it on every change and weekly against SeaweedFS, RustFS, moto and Azurite. All pass. The README explains how to point it at your own bucket or container.

## Known limits

- Still not run against a real AWS or Azure account. If you have one, running `tools/cloud-conformance/run.sh` against a test bucket and telling us the result is the most useful thing you can do for the project.
- Everything in the v1.6.0 and v1.6.1 notes still applies.
